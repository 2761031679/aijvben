## 0. 为什么需要这份东西

同一套「组合信息目录 + 体验状态机 + 标记协议」，现在要同时被四处使用：

| 使用方 | 语言 | 角色 |
|---|---|---|
| Web 前端（jvben.cn） | JavaScript | 有 UI，服务玩家 |
| MCP 插件（新） | Python | 无 UI，服务第三方 AI |
| 任意 AI 客户端 | 任意 | 只认 HTTP/JSON 与 MCP 协议 |
| 后端 | Python | 唯一的真相源 |

现状是「组装逻辑在浏览器里」，插件用不了。本契约把这五件事固化成协议：

1. **谁能看到什么**（凭证 → 主体 → 能力）
2. **按什么顺序拼成什么结构**（分节 + 配方）
3. **AI 输出什么文本会被识别成什么指令**（标记）
4. **一次体验的生命周期怎么走**（状态机 + 相位）
5. **凭证怎么签发、怎么失效、怎么防泄露**

> 铁律一：**契约里没有任何「AI 该怎么说话」的规则**。说话规则在
> `npc_configs/**/prompts/*.txt` 里，由宿主 AI 的 system prompt 承载。契约只管**结构**。
>
> 铁律二：**服务端只从凭证推导身份，永不接受客户端声明的身份。** 客户端说自己「是主持人」
> 没有任何意义，它得拿出主持证。

## 1. 术语

| 术语 | 含义 |
|---|---|
| **Actor（主体）** | 请求身份。`guest`（游客）/ `user`（登录玩家）/ `host`（主持方） |
| **Capability（能力）** | 主体拥有的能力字符串，**闭集**。权限判定的唯一依据 |
| **长期钥匙** | 用户自己生成、长期有效的凭证，代表「我是这个玩家」。贴到第三方 AI 配置里用 |
| **本场主持证** | 开房那一刻服务端签发的临时凭证，只对那一场、那一本剧本有效 |
| **Section（分节）** | 上下文的一个分节（如「A 角色设定」） |
| **Group（组）** | 若干分节合并后的顶层键（如「A 角色设定」整块） |
| **PromptBundle** | 一次组装的完整结果 |
| **Session（会话）** | 一次剧本体验的生命周期对象 |
| **Phase（相位）** | 会话的服务端状态：`hosting / settling / ended`（三相，无 `preparing`） |
| **Marker（标记）** | AI 输出文本里嵌的指令，形如 `[verb:arg]` |

## 2. 凭证与主体

### 2.1 三种凭证，三种身份（**身份由凭证种类决定，不是由字段声明**）

| 携带的凭证 | 推导出的主体 | 能力范围 |
|---|---|---|
| 无 / 游客 cookie | `guest` | 游客只读 |
| 用户 JWT（**长期钥匙**换来的，或网页登录态） | `user` | 玩家该有的一切 |
| 主持证（**本场主持证**） | `host` | 仅本场主持权 |

```json
{ "kind": "guest", "id": "gz_7f3a", "role": "guest",
  "capabilities": ["script:read", "session:start_free"] }

{ "kind": "user",  "id": "u_abc", "role": "normal", "user_id": "u_abc",
  "capabilities": ["script:read", "script:read_pending", "script:read_answer",
                   "script:write", "clue:read", "clue:write",
                   "session:start", "session:start_free", "session:settle",
                   "social:vote", "social:report", "social:follow", "social:rate",
                   "profile:read", "profile:write"] }

{ "kind": "host",  "id": "h_9x",   "role": "host",
  "session_id": "ps_123", "script_id": "5e804ffa8fe4",
  "capabilities": ["script:read", "script:host", "clue:write", "session:settle"] }
```

`role` 取值沿用现有五级：`guest` / `normal` / `station_master` / `admin` / `owner`。

> **`host` 不是 users 表里的角色**，它是会话引擎为「正在主持」这一刻签发的临时主体。
> **一次请求里不能同时是 host 和 user。** 需要两种身份就发两次请求、换两次凭证。

### 2.2 能力闭集

```
script:read              读 approved 剧本的公开字段
script:read_pending      读未过审剧本（admin / owner / 作者本人）
script:read_answer       看「汤底一句话」（详情页解锁；见 §10）

script:host              取「主持专用全套」——汤底 + 结束条件 + 触发信号表 + 主持指导词
script:write             上传 / 修改剧本

clue:read                读线索 / 道具面板
clue:write               改线索 / 道具面板

session:start            开一场体验（不带免费额度语义，走正常计费/无计费）
session:start_free       走免费活动额度开一场体验
session:settle           触发结算

social:vote / social:report / social:follow / social:rate
profile:read / profile:write
admin:read / admin:write
```

**未知能力名一律拒绝**（白名单，不做通配）。

### 2.3 ⚠️ `script:read_answer` 与 `script:host` 的区别（v1 在这里写错过）

这两个**不是**一件事，v1 用同一个判据管它们，导致「订阅+通关的玩家能看汤底」与「没有主持权就删汤底」直接打架。

| 能力 | 给的是 | 谁能有 |
|---|---|---|
| `script:read_answer` | **只有**「汤底/真相」那一段文字 | 作者本人 / 订阅该剧本且已通关 / admin / owner / host |
| `script:host` | **整套**：汤底 + 结束条件 + 胜利失败条件表 + 任务条件表 + 主持指导词 | **只有** host（以及 admin/owner 的调试态） |

**取主持上下文时，删的是「主持专用字段」，判据是 `script:host`，不是 `script:read_answer`。**
一个只有 `script:read_answer` 的玩家来请求主持上下文，他拿到的是标题、谜面、线索面板、玩家信息，
**没有条件表、没有触发信号、没有主持指导词、没有汤底**——他在详情页本来就能看汤底，所以不构成新泄露。

## 3. Context 请求

```
POST /api/host/context
Authorization: Bearer <user-jwt | 主持证 | 无（游客）>
X-Host-Token: <主持证>            # （v1.3 新增，可选）与长期钥匙并存时用这个头
Content-Type: application/json
```

> **凭证放在哪个头（v1.3 补充，实现时发现的必要补充）**
>
> `Authorization` 一个头装不下两个身份。有两类调用方：
>
> - **纯第三方主持人**：没有玩家身份，只有主持证 → 主持证放 `Authorization`。
> - **玩家自己的浏览器**：既登录着（`Authorization` 放长期钥匙），又正主持这一场
>   （手里有主持证）→ 主持证放 **`X-Host-Token`**。
>
> 服务端两个位置都认，`X-Host-Token` 优先。只带 `X-Host-Token` 的请求语义是
> 「我是这个玩家，同时我正在主持这一场」——它**不会**让调用方获得该玩家的权限，
> 只解开「这一场的主持权」。

```json
{
  "contract": "aijuben.context/1.3",
  "state": "default | browsing | experience",
  "npc_id": "jingyuniang | xiaoshuai | xiaomei | dagou",
  "session_id": "ps_xxx | null",
  "locale": "zh-CN"
}
```

`state=experience` 时 `session_id` 必填，且**必须是这张凭证绑定的那一场会话**：

| 凭证 | 合法的 `session_id` |
|---|---|
| `user` | 该玩家自己开的会话（`owner_user_id` = 他） |
| `host` | 主持证里写死的那一场（**不要求**他是会话主人——主持人可以是别人） |
| `guest` | 游客会话（`owner_user_id` = null），且只能体验免费剧本 |

> v1.1 原文写「必须属于当前主体」，对 `host` **不可满足**：主持证主体没有 user 身份，而会话属于玩家 → 按字面必然 403。这是评审 A11，v1.2 改正。

### 4.1 硬约束

- `system_prompt` 是**最终产物**：等价于 `JSON.stringify(root, null, 2)`
  —— **缩进 2 空格、换行、不转义中文**（与 `frontend/js/modules/npc/prompt_builder.js:135` 现有行为逐字节一致）。
  **不是**紧凑无空格 —— v1.1 写「紧凑、无空格」是与代码相反的，照它写黄金样本会全红（评审 A2）。
- `root` 与 `system_prompt` 必须自洽：解析 `system_prompt` 必须得到 `root`。
- 顶层**只有两个包装键**，字面量照抄、一个空格都不许差：
  1. `工作流程（最高优先级，务必逐级严格遵循）`
  2. `资料库（按需查阅）`
- A–I 这些分组是 `资料库` 的**子键**，不在顶层。
- `工作流程` 节**恒在**（三态都有），来源固定为 `thinking_mode`。
- 消费端**不得再次改写 `system_prompt`**，只能原样塞进 `role:"system"`。
- 这条是「前端和插件不再各自漂移」的技术保证。

### 4.2 内容指纹 `prompt_hash`（v1.1 新增）

`prompt_hash` = `system_prompt` 的 UTF-8 字节做 SHA-256，取前 16 位十六进制。

**运行时要校验，不能只靠 CI 静态断言：**

| 场景 | 消费端行为 |
|---|---|
| 双跑期（前端同时有本地实现） | 本地也算一遍，**与 `prompt_hash` 比对**；不一致 → 上报告警，**但仍使用服务端的** |
| 前端有本地缓存 | 服务端返回的 hash 与缓存不符 → 缓存作废，重新渲染 |
| 插件 / 第三方 AI | 只记录，不回算（它们没有第二份实现） |

### 5.1 三条合并规则（v1.2 重写 —— v1.1 把两件事用一条判据管了，评审 A3）

**这三条是三件不同的事，不要互相套用：**

**规则 1 · 回退链** `a|b`：分节 `a` 内容为空（`""` / `null` / 空数组 / 空对象）时取 `b`。

**规则 2 · 同一组内多个分节 → 嵌套对象**（键名取下表，**不是数组**）

组内只有 1 个有效分节 → 直接输出该分节的 `content`；
多于 1 个 → 输出**对象**，子键取 `_SECTION_KEYS`：

| 分节 | 子键名（逐字照抄） |
|---|---|
| `soul` | `角色设定` |
| `guide` | `网页面板引导` |
| `sidebar_guide` | `侧边栏状态引导` |
| `greeting` | `开场规则` |
| `iron_rules` | `铁律` |
| `tools` | `工具手册` |
| `sidebar_tools` | `侧边栏工具` |
| `mode_rules` | `模式规则` |
| `script_info` | `剧本内容` |
| `experience_tools` | `剧本体验工具` |
| `inventory` | `线索/道具面板（当前状态，每轮实时更新；序号即 remove 指令的 index 参数）` |
| `capability` | `表情控制` |
| `status_bar` | `状态栏 UI（可操作）` |

**这张表只有 13 项**（`prompt_builder.js:26-43` 的 `_SECTION_KEYS`）。
`output_style` / `thinking_mode` / `player_info` / `__markers__` **不在表内** ——
它们目前都属于「单分节组」或顶层独立渲染，不查子键表，直接输出内容。
v1.1 把它们的子键名（`输出规范`/`思考方式`/`玩家信息`/`标记手册`）写进表里是凭空的，已删除。

**⚠️ 这条最容易做错：回退命中时，子键名不变。**
`_renderGroup` 取的是 `_SECTION_KEYS[sec.split('|')[0]]` —— 取**回退链左边**的名字。
所以 browsing 态若 `sidebar_guide` 为空、回退到 `guide`，输出仍是
`{"C 侧边栏引导": {"侧边栏状态引导": <guide 的内容>, "开场规则": …}}`，
**不会**变成 `网页面板引导`。

**⚠️ 今天真正用到这张表的只有 3 个子键。**
三张配方里「组内多于 1 个分节」的仅两处：

| 状态 | 组 | 分节 | 实际输出的子键 |
|---|---|---|---|
| default | `C 网页面板引导` | `guide`, `greeting` | `网页面板引导`, `开场规则` |
| browsing | `C 侧边栏引导` | `sidebar_guide\|guide`, `greeting` | `侧边栏状态引导`, `开场规则` |

其余组都是单分节（`sidebar_tools|tools` 也算单分节，因为回退链是一个分节），
直接输出内容、不包对象。**不要因为表里有 13 项就以为会输出 13 层嵌套。**

> 子键表以 `frontend/js/modules/npc/prompt_builder.js:26-43` 的 `_SECTION_KEYS` 为唯一权威；
> 实现时**照抄那份表**，本表只是快照。缺项时回退用分节名本身。

**规则 3 · 同一 `prompt_type` 有多份文件内容 → 数组**

例：某 NPC 私有 `tools` + 共享 `tools` 都在配方里 → `[私有内容, 共享内容]`。
这才是数组出现的**唯一**场景。

> 一句话记法：**多分节 → 对象；同类型多文件 → 数组。**

### 5.2 分节来源类型

| `source` | 出处 |
|---|---|
| `npc_file` | `npc_configs/{npc_id}/prompts/{key}.txt` |
| `shared_file` | `npc_configs/shared/prompts/{key}.txt` |
| `db` | `npc_prompts` 表（历史遗留；**仅在文件缺失时兜底**） |
| `dynamic` | 由会话引擎实时生成（`script_info` / `inventory` / `status_bar` / `mode_rules`） |
| `generated` | 由代码生成（`capability` / `__markers__` / `player_info`） |

文件内容是 JSON 时解析为对象；不是 JSON 时**按原始字符串容错嵌入**（现有行为，不能改）。

### 5.3 会话数据结构 `session_data`（v1.1 新增，**随本契约一起冻结**）

v1 说「第二期实现时再冻结」，这等于前两期没有依据。现提前冻结：

```json
{
  "schema": 2,
  "phase": "hosting",

  "owner_user_id": "u_abc",
  "script_id": "5e804ffa8fe4",
  "npc_id": "jingyuniang",
  "mode": "turtle_soup",

  "inventory": { "clue": [], "item": [] },
  "cond_counts": { "e1.c1": 1, "e1.c2": 1 },
  "task_counts": { "t1.c1": 0 },

  "settled_ending": null,
  "ending_type": null,
  "settlement": null,
  "narrated": false,
  "last_words_used": 0,

  "turn_lock": { "holder": null, "expires_at": null },
  "revoked_at": null,

  "started_at": "2026-10-26T12:40:00Z",
  "last_active_at": "2026-10-26T13:04:58Z"
}
```

| 字段 | 说明 |
|---|---|
| `schema` | 结构版本。读取时低版本按默认值补齐，**只为兼容旧会话而存在** |
| `phase` | 服务端权威相位，前端只读 |
| `inventory.clue/item` | 字符串数组。序号 = 数组下标 + 1，与 `[sys:remove_clue:index=n]` 对应 |
| `cond_counts` | 条件计数，键是 `结局ID.条件ID`。**幂等**：同一键只增一次 |
| `task_counts` | 同上，任务条件 |
| `settled_ending` | 已达阈值的结局 ID，`null` 表示未结算 |
| `settlement` | 结算产出（金币/经验/等级/解锁），落库成功后写入 |
| `narrated` | **解说是讲完了**。这是 `settling → ended` 的必要条件（见 §7.3） |
| `last_active_at` | 最后一次有效请求时间。闲置回收与安静超时都看它 |
| **`owner_user_id`** | **（v1.2 新增）** 开房玩家。`host` 主体没有 user 身份，组装 `I 玩家信息`、`player`、判配额时**一律取这个字段**，不看请求主体 |
| **`ending_type`** | **（v1.2 新增）** `"win"` / `"lose"`。**结算落库必须分支**：`lose` 只写结局记录，**不写通关、不发奖励、不解锁汤底**（现网 `settlement.js` 的 `showDefeat()` 就是这个行为，v1.1 漏了） |
| **`settlement` 结构** | **（v1.2 明确）** `{ "coins": 50, "exp": 100, "level": 3, "unlocked": true, "recorded": true }`；`null` = 未结算 |
| **`last_words_used`** | **（v1.2 新增）** 遗言轮计数 0/1。这是「已 ended 但主持证还能用一次」的唯一凭据（§7.3） |
| **`turn_lock`** | **（v1.2 新增）** 并发锁。`{holder, expires_at}`；`expires_at` 过期即视为无主，**进程崩了也能自愈**（v1.1 说放内存，崩了就永久 409） |
| `revoked_at` | 主持证撤销时间，`null` = 未撤销 |

> 改这个结构 = 改 `session.schema` 版本号，不许悄悄加字段。

## 7. 状态机

### 7.1 顶层态（Web 网页状态，沿用现有实现）

```
        ┌──────────── 侧边栏打开 ────────────┐
        ▼                                    │
   ┌─────────┐  ── 侧边栏关闭 ──►  ┌──────────┐
   │ default │                     │ browsing │
   └────┬────┘  ◄── 侧边栏关闭 ──  └────┬─────┘
        │                               │
        └──── start_experience ─────────┘
                     │
                     ▼
              ┌────────────┐
              │ experience │
              └─────┬──────┘
                    │ 退出 / 结算 → returnFromExperience
                    ▼
              （回到进入前的态）
```

规则：
- `experience` **不被侧边栏开关打断**（体验中打开侧边栏，状态仍是 `experience`）。
- 进入体验时记录返回态；退出/结算回到它（非法值回落 `default`）。
- 同状态重复设置只更新元信息，不触发钩子与提示词重组。

### 7.2 Session 相位（新增，**服务端权威**）

```
                    ┌── 条件达阈值 ──► settling ──narration.done──► ended
                    │                     │                         ▲
session/start ──► hosting                 └──── session/end ────────┘
                    │                                               ▲
                    └────── session/end（reason=aborted）───────────┘
```

**三个相位，没有第四个。**（v1.1 画了 `preparing` 但全文档没有任何事件能进入它——评审 B3，已删。）

| 事件 | 迁移 | 副作用 |
|---|---|---|
| `session/start {script_id, npc_id}` | ∅ → `hosting` | 建会话、**签发主持证**、装填线索面板、扣额度 |
| `marker.cond {ending_id, cond_id}` | `hosting` → `settling`（达阈值的同一请求内） | 条件计数 +1（幂等）；达阈值 → 进 `settling` **并在同一事务里立刻落库**（见 §7.3） |
| `narration.done` | `settling` → `ended` | 产出结算结果、**主持证降级为遗言证**（不撤销）、主体降级 |
| `session/end {reason}` | 任意 → `ended` | `reason ∈ {settled, aborted, timeout}`；`aborted` **不落库** |

> **`ended` 之后玩家想再玩**：重新 `session/start` 开一个新会话；旧会话保留为「未完结」记录，不复活。
> v1.1 的相位图里 `ended` 没有出边，玩家会无路可走（评审 B6①）。

### 7.3 时序铁律（这是「真相被截断」的修法）

> **先解说、后撤上下文。**

`settling` 相位下主持上下文**仍然有效，且必须继续可请求**。
只有「结局解说」这一轮输出完成（`narrated = true`）之后，才允许 `ended` 并撤销主持证。

**禁止**在 AI 正在流式输出的同一轮里撤销上下文。现网 bug 就是：
结算在流式未结束时触发 → 「通知 AI 用结局备注解说」这一步被整段跳过 →
紧接着退出体验态摘掉主持上下文 → AI 只讲 111 字就断。

#### 超时：不用固定秒数，用「安静超时」

v1 写「等解说完成或超时 60 秒」。这是错的——**解说本身就在那一轮输出流里，流可能超过 60 秒，掐断等于又切半句**。

| 机制 | 定法 |
|---|---|
| **安静超时** | 连续 **300 秒**（5 分钟）没有任何请求才算超时。只要还在出字就不算 |
| **心跳续期** | 客户端每次请求（含流式过程中的分片上报）刷新 `last_active_at` |
| **超时后** | 转 `ended`。**主持证不撤销**，降级为「遗言证」。**同时补做一次幂等落库**（若结局已达成但未落库——评审 A7）。 |
| **遗言轮** | 凭遗言证可调用 `session/turn` **恰好一次**，服务端按 `experience` 配方返回上下文，**不重复记账、不重复落库**；调用后 `last_words_used = 1`，**随即撤销主持证**（此后一切请求 `410`） |

遗言轮的设计目的：**最坏情况下也把话讲完**，而不是重演截断。

> **v1.1 在这里自相矛盾（评审 A4）**：一边写「超时后撤销主持证」，一边写「凭旧主持证仍可调用一次」，
> 还同时写「撤销后的一切请求必须 410」。同一张证不可能既失效又可用。
> **v1.2 定案：`ended` 不撤销证，而是把证降级成「只许用一次」的遗言证；用完即撤销。**
> 这也让「撤销」有唯一含义：**撤销 = 从此 410**。

### 7.3.1 结算时序：先落库，后解说（v1.2 修正，评审 A6/A7）

**顺序不许颠倒：**

```
① 条件达阈值          → 相位 settling
② 立刻落库（幂等）     → 按 ending_type 分支：win 记通关 + 发奖励 + 解锁汤底；lose 只记结局
③ 组解说上下文         → 取「结局备注」+ 主持专用全套
④ 解说那一轮           → AI 输出结局解说
⑤ narrated = true     → 相位 ended
```

**为什么 ② 必须在 ④ 之前**：现网 `settlement.js` 的注释就是「胜利先调通关接口落库，再展示面板，
玩家看到面板前数据已安全」。v1.1 把落库绑在解说之后，等于**主持人 AI 一旦卡住/断线，玩家赢了也不算数**。

**为什么 ② 必须按 `ending_type` 分支**：现网 `showDefeat()` 明确「不标记通关、不解锁汤底、无奖励」。
v1.1 的结算链没有任何分支，照它实现会把**失败结局当通关处理，还解锁汤底**——这是明确的行为回退。

### 7.4 主持证生命周期（v1.1 新增）

| 项 | 定法 |
|---|---|
| **有效期** | 签发时 4 小时封顶；每次有效请求自动续期 |
| **撤销时机** | ①结算落库完成**且**遗言轮已用尽 ②`session/end{reason:aborted}` ③玩家主动结束 ④闲置 300 秒转 `ended` **并等到遗言轮用尽** ⑤签发满 4 小时 |
| **关网页怎么办** | **不撤销**。网页关了不代表这场结束——AI 可能还在主持。靠闲置超时回收 |
| **并发** | 同一张主持证，**同一时刻只允许 1 个 `turn` 在处理中**。第二路直接 `409 session_busy`。锁**落库**（`session_data.turn_lock`）而不是放内存——放内存的话进程一崩就永久 409 直到会话超时（评审 A5④） |
| **锁与超时的量级关系** | 锁 120 秒，远短于闲置超时 300 秒。反过来（锁比超时还长）就会「人早走了、锁还占着」。一轮超过 2 分钟的长解说必须**中途续锁**，不能靠加大这个数 |
| **跨设备** | 允许。主持证不绑 IP、不绑 UA，只绑会话 |
| **可撤销多次调用** | 幂等。已撤销的主持证再撤销返回成功，不再报错 |

### 8.1 全量标记表

| 标记 | 生效态 | 语义 | 是否产生副作用 |
|---|---|---|---|
| `[emotion:表情id]` | 全 | 播表情 | 否（纯渲染） |
| `[action:动画id]` | 全 | 播动画 | 否 |
| `[SEGMENT]` | 全 | 分段 | 否 |

| `[guide:目标名]` | 全 | 引导高亮圆环 | 否 |
| `[options:标题1:备注1\|标题2:备注2]` | default / browsing | 出 2~4 个选择题 | 否 |
| `[tool:工具名:参数1=值1&参数2=值2]` | default / browsing | 查站内真实数据 | **是（查库）** |
| `[tool:history]` | 全 | 回想历史对话 | **是（查库）** |
| `[btn:文字:open_tutorial:模型ID]` | default / browsing | API 获取教程按钮 | 否 |
| `[sys:start_experience:script_id=ID]` | default / browsing | 开剧本体验 | **是** |

| `[sys:report_issue:reason=…]` | 全 | 上报提示词缺失/系统问题 | **是（落库）** |
| `[answer:yes\|no\|both\|irrelevant\|unable]` | experience | 海龟汤作答 | 否（转文字） |
| `[cond:结局ID.条件ID]` | experience | 条件达成信号 | **是（计数+可能结算）** |
| `[task:任务ID.条件ID]` | experience | 任务条件信号 | **是（计数）** |
| `[sys:add_clue:content=…]` | experience | 加线索 | **是** |
| `[sys:remove_clue:index=n]` | experience | 删线索 | **是** |
| `[sys:add_item:content=…]` | experience | 加道具 | **是** |
| `[sys:remove_item:index=n]` | experience | 删道具 | **是** |
| `[do:指令]` | experience | 分段延迟执行 | **是（执行内层）** |
| `[sys:end_experience]` | experience | 主动结束体验 | **是** |

### 8.2 解析与执行必须拆成两个动作（v1.1 修正）

v1 一边说「解析是纯函数、不产生副作用」，一边让解析模块承担 `[tool:…]` 的执行分发——
自相矛盾。**现明确拆分：**

#### 动作一：认字（纯函数，不碰任何数据）

```
parse(text, state, whitelist) -> ParseResult { plain, segments[], markers[] }
```

- 同样输入永远同样输出
- **不查库、不写库、不改会话状态**
- 只做四件事：①把标记从正文剥掉 ②按 `[SEGMENT]` 切段 ③把每个标记拆成 `{verb, args}` ④按白名单校验合法性

#### 动作二：执行（有副作用，另起一步）

```
apply(session, markers, actor) -> ApplyResult { state_changes[], tool_results[], settlement? }
```

- 按顺序施加副作用：查库、改线索、推条件、触发结算、落库
- **只有它允许访问数据库**
- 认字过程发现未知标记 → 放进 `markers` 并标 `ok:false`，由执行步决定丢弃还是报错，**认字步自己不抛错**

#### 解析规则（两端必须一致）

1. 标记**不展示给玩家**，只执行。
2. 一段（`[SEGMENT]` 之间）最多 **1 个 `emotion` + 1 个 `action`**。
3. 标记 id 必须在白名单内（表情/动画来自 NPC 配置，条件 id 来自剧本条件表）；
   未知 id **丢弃并记 warning**，不得抛错中断。
4. `[cond:]` / `[task:]` **幂等**：同一 `(session_id, ending_id, cond_id)` 只计一次。
5. `[do:…]` 在它所在的那一段渲染完之后执行。

| `POST` | `/api/host/session/start` | **长期钥匙 或 游客**（`host` ❌，见 §11.3） | `{script_id, npc_id}` → `{session_id, phase, host_token, expires_at}` |
| `POST` | `/api/host/session/turn` | **主持证** | `{session_id, reply_text}` → 见下 |
| `POST` | `/api/host/session/{id}/settling` | **主持证** | 声明「结局成立，进入结算相位」。条件系统判定那一刻调一次，幂等 → `{phase, narrated}` |
| `POST` | `/api/host/session/{id}/narrated` | **主持证** | 声明「结局解说说完了」。**只在真的讲完之后调** → `{phase, narrated}` |
| `POST` | `/api/host/session/end` | **主持证** | `{session_id, reason}`，`reason ∈ {settled, aborted, timeout}` → `{phase}` |
| `GET` | `/api/host/session/{id}` | **该会话的主持证**；或会话主人自己的长期钥匙 | 会话快照 |
| `GET` | `/api/host/ui-meta` | 无需（公开） | 界面元数据：`ui_targets`、`status_uis`（顺序固定 mode→hp→conditions）、`emotions`、`animations`。**这是这些常量的唯一真源**，前端不再各存一份 |

> **`settling` / `narrated` 为什么必须显式存在（v1.3）**
>
> §7.3 的铁律是「先解说、后撤上下文」，而这条铁律要落地就必须有一个可观测的中间态。
> 少了它，`end{reason:settled}` 的两条前置条件（相位已是 `settling`、`narrated=true`）
> 永远不可能同时成立 —— 于是「正常结算」在服务端根本走不通，客户端只能一直用 `aborted`
> 收场（实现了闸门却没人能走对）。反过来，这两个端点也堵住了「主持中直接喊 settled
> 跳过整段解说」这条路。

`session/turn` 返回：

```json
{
  "plain": "……", "segments": ["……"], "markers": [],
  "phase": "hosting | settling | ended",
  "inventory": { "线索": [], "道具": [] },
  "settlement": null,
  "ending_type": null,
  "narrated": false,
  "last_words_left": 1
}
```

> `prompt_hash` **不在 `session/turn` 返回里**（v1.1 放了，但语义未定义：一轮对话并不重组上下文，
> 重组只发生在 `session/start` 与结算后重置——评审 B10）。它只在 `POST /api/host/context` 返回。

**`settling` 相位下 `session/turn` 仍可调用**——这就是解说的那一轮，也是超时后的遗言轮。

### 9.4 MCP 凭证与插件端点（P4 追加）

插件（`server/mcp-server/`，见其 `README.md`）与站点之间只有 HTTP，凭证有两种：

| 凭证 | 放哪 | 用途 |
|---|---|---|
| **玩家长期钥匙**（JWT）或 **MCP 门票**（`mcp_` 前缀） | `Authorization: Bearer <…>` | 代表「某个玩家」 |
| **主持证**（不透明随机串） | `X-Host-Token` | 代表「正在主持这一场」 |

> **`mcp_` 前缀是硬约定。** 主持证的识别口径是「不含点、且 ≥40 位」，而 MCP 门票正好长这样
> （`mcp_` + 43 位）。`host_session_service.raw_from_headers` 必须显式排掉 `mcp_` 开头的值，
> 否则「只带门票、不带 `X-Host-Token`」的请求会拿到一张查不到的证，连不需要凭证的
> `default` / `browsing` 上下文都会被判 401。**主持证永远不要塞 `Authorization`。**

`scopes` 是**上限**不是快照（§15 同一口径）：实际生效能力 = 门票授权 ∩ 该用户此刻本该有的能力。

| 能力名 | 覆盖 |
|---|---|
| `script:read` | 读剧本列表/详情/标签（**永远不含汤底**） |
| `session:host` | 开房、取体验上下文、心跳、相位推进、收场 |
| `session:settle` | `settling` / `narrated`（单独拆出来：结算相位只该给真正在主持的那条通路） |
| `player:read` | 读自己的档案/统计/作品/收藏 |
| `write:script` | 上传/修改剧本（v1 未开放执行） |
| `social:vote` / `social:report` / `social:follow` | 投票 / 举报 / 关注（v1 未开放执行） |

| 方法 | 路径 | 需要 | 用途 |
|---|---|---|---|
| `POST` | `/api/user/mcp-tokens` | 长期钥匙 | `{name, scopes[]}` → 201 `{id, name, scopes, created_at, token, note}`。**`token` 明文只返回这一次**，库里只存 `sha256(id + 明文)`。`note` 如实说明「scopes 只区分动作大类、不细分数据范围；门票进不去管理面、也不能再签门票」 |
| `GET` | `/api/user/mcp-tokens` | 长期钥匙 | 列出自己的门票（**永不含 token / token_hash**） |
| `DELETE` | `/api/user/mcp-tokens/{id}` | 长期钥匙 | 吊销（幂等，204）；不是自己的 → 404（不泄露存在性） |

**v1.3 补：`scopes` 现在真的执行**（审计 M1/M2 —— 此前 `capabilities_for_user()` 恒返回全量，
`_mcp_scopes` 挂到 User 上之后**全项目零读取**，所以一张 `["player:read"]` 的门票等于把账号
原样外包，且能给自己再签一张）：

| 规则 | 实现位置 | 拒绝时报 |
|---|---|---|
| 门票**一律不得进入** admin / owner / station_master 面（不是「再判一次级别」，是「门票 ≠ 管理员」写死：账号本人是管理员也一样拒） | `backend/core/security.py` `_deny_by_token()`，挂在 `require_admin` / `require_admin_or_station_master` / `require_owner` 三个守卫尾部 | 403 `capability_denied` |
| 开房要 `session:host` | `backend/routers/host.py` `_check_ticket_scope()` | 403 `capability_denied`（`detail.needed` 列出缺哪几个） |
| `settling` / `narrated` 要 `session:settle` | 同上 | 同上 |
| 门票**不能签发 / 列出 / 吊销门票**（否则吊销形同作废：吊销前先自签 10 张） | `backend/routers/user.py` 三个端点改用 `Depends(require_login_not_token)` | 403 `capability_denied` |
| 普通登录态与匿名**完全不受影响** | `require_scope()` 只在「本次请求作者是门票」时生效；开房对匿名直通 | — |

### 9.5 前端可观测事件上报（P4 追加）

| 方法 | 路径 | 需要 | 用途 |
|---|---|---|---|
| `POST` | `/api/log/client-event` | 公开 | 把「只发生在浏览器里、服务端看不见」的事件落进 `access_logs` |

- 目前唯一白名单事件：`host_degraded` → `action="M30b降级"`，`detail` 形如
  `reason=连不上主持通道 count=3 state=experience`。
- **永远返回 204**，非白名单事件也静默吞掉 —— 上报失败绝不能反过来打扰玩家。
- 字段一律截断（事件名 40 / 其余 80~200 字符），走全局限流（30 请求/10 秒）。
- 存在理由：`window.__hostDegraded` 之前**只写不读**，运营侧对「降级发生了多少次」全静默。

规则：

- 单人最多 **10** 把活跃门票，超了 409 `token_limit_reached`。
- 每张门票 **60 次/分钟**，超了 429 `rate_limited`（附 `retry_after`）。
- `scopes` 里出现系统不认识的能力名 → **忽略并告警，不拒绝**（否则升级瞬间老钥匙全废）；
  但整形后为空集 → 该门票无效，401 `no_actor`。
- 每次带门票的请求写一条 `access_logs`（`action="MCP调用"`，带路径、IP、`X-Mcp-Tool` 头里的工具名）。
- 门票**只代表玩家**，永远不产生主持证；要主持必须再走 `session/start` 拿证。

### 10.1 现存越权路径与整改清单（v1.2 新增，评审 A1 / A12）

**先说一件已经在发生的事。**

`GET /api/npc/scripts/{script_id}` 对海龟汤类型**无条件返回完整内容**：汤底、结束条件、
胜利失败条件表、任务条件表、主持指导词，全套。它用「可选登录」，**游客不带任何凭证也能调**；
而且**支持按标题模糊匹配**——输「跳楼」就能捞到《跳楼的女人》的汤底。
代码注释自己写明：「汤底对『玩家直接查看』的保密……**不由此接口过滤**」。
这条路径**已经被包成给 AI 主持人调用的工具**（`frontend/js/modules/npc/tools.js:64`）。

**后果**：§10 的矩阵、§14 的三道防线、新方案的「唯一闸口」叙述，全都被这条路径旁路掉了。
**方案 M24 自称「汤底分发的唯一闸口」是错的**——旧的闸门一直开着，而且 M12 还打算把它开放给插件。

#### 整改方案：保留联想度，但把「搜得到」和「看得到汤底」拆开

用户明确要求保留搜索引擎式的联想体验（用「跳楼」能找到《跳楼的女人》）。
**这个体验必须保留。真正要拆的是两件事：能不能搜到 ≠ 能不能看到汤底。**

| 场景 | 现状 | 整改后 |
|---|---|---|
| 按标题模糊**搜**剧本 | 返回完整内容 | **照旧可搜**，但只返回公开字段（标题 / 类型 / 难度 / 标签 / 简介 / 谜面） |
| 取**汤底与主持全套** | 无门槛 | 必须**同时**满足三条：① 有登录凭证；② 该剧本**有他正在进行的体验会话**（或他是作者 / admin / owner）；③ 该会话的 `script_id` 与本剧本一致 |

**一句话：拿汤底的钥匙是「正在主持这一场」，不是「登录过」。**

这样联想度一点不减——搜索永远搜得到；而汤底只有真的在玩的人、且只在他自己那一场里拿得到。

#### 实现要点

1. **`include_full` 由服务端判权决定**，客户端传什么都不算。默认返回公开字段。
2. 完整内容走新通道 `POST /api/host/context`（§9.2），凭证是**本场主持证**。
3. 模糊匹配**保留**，范围限于 `review_status = approved` 且 `is_deleted = false`，**结果绝不含主持专用字段**。
4. 返回主持专用字段**必须写审计日志**（§14 防线三）。
5. 过渡期（P0–P1）：旧接口的 `include_full=True` 分支先加「存在进行中会话」校验；P2 起由 M24 完全接管。

#### 同批整改的其他裸入口（评审 A12）

| 入口 | 现状 | 整改 |
|---|---|---|
| `GET /api/scripts/{id}`（详情页） | 只判 `is_deleted`，**不判是否过审** | 未过审仅作者 / 管理员可见，其余 404 |
| `POST /api/game/{id}/start`（开体验） | 只判 `is_deleted` | 同上，未过审返回 `423` |
| `POST /api/game/{id}/ask`（提问） | 只判 `is_deleted` | 同上 |
| `POST /api/game/{id}/hint`（提示） | **把汤底按句拆开逐句吐给玩家**；且只有登录用户才计数 → **游客可无限次把汤底全拉出来** | ① 提示改为服务端生成，**不得回吐汤底原句** ② 游客同样计数并受 IP 限流 |

> 最后一行是本次审计第二严重的发现：**「提示」功能本身就是一条汤底侧信道**，且游客侧计数失效。

### 10.1.1 字段分三档（比「公开 / 保密」两档更细）

| 档 | 谁拿得到 | 包含 |
|---|---|---|
| 公开 | 任何人 | 标题、类型、难度、标签、简介、谜面 `story` |
| 条件表 | 正在主持这一场的人（持主持证）、或该剧本作者/管理员/站长 | `ending_condition`、`endings`、`tasks` |
| 汤底 | **只在服务端**。任何面向浏览器的接口都不下发 | `explanation`、`host_guide` |

为什么条件表要单独一档：浏览器要靠它判定「玩家识破了没有」（条件标记 `[cond:结局.条件]` 是前端解析的），但条件表不是汤底正文。

为什么汤底要彻底不下发：提示词现在由服务端组装（§9.2 `POST /api/host/context`），浏览器只报「我在什么状态、主持哪一场」，汤底全程不出服务器。验收标准不是「接口防得住」，而是**正常游玩、不翻前端源码、不抓包的人碰不到汤底**。

## 11. 两种 AI 模式（v1.1 重写）

### 11.1 模式由凭证决定，不由字段声明

| | **代理模式**（AI 代表玩家） | **主持模式**（AI 当主持人） |
|---|---|---|
| 携带凭证 | 玩家的**长期钥匙** | 服务端签发的**本场主持证** |
| 主体 | `kind:"user"` | `kind:"host"` |
| 能看汤底 | **只能看到详情页那一句「汤底/真相」**（凭 `script:read_answer`）；**体验上下文里一律不带汤底**（§6.2 精简版 3 键） | ✅ 本剧本全套（`script:host`） |
| 能写剧本 / 投票 / 关注 | ✅（等同玩家本人） | ❌ |
| 能推条件标记 | ❌ | ✅ |
| 能开房 | ✅ 用玩家自己的额度 | ❌ |
| 典型场景 | 玩家让 AI 帮自己玩 / 帮自己上传剧本 | 玩家让 AI 当主持人服务自己或别人 |

> **v1 的错误设计**：给长期钥匙加了一个 `mode` 字段，等于说「这把钥匙只能干一种事」。
> 而长期凭证是长期有效的，模式却是每次请求的事——两者根本不该绑在一起。
> **v1.1 定案：删掉 `mode` 字段。身份 = 你拿的是哪把钥匙。**

### 11.2 同一插件实例两种模式并存，怎么办

插件里可以同时配置两把钥匙，按场景选：

```
玩家问「帮我看看这个剧本」        → 用长期钥匙（代理模式）
玩家说「你当我这本剧本的主持人」  → 先开房拿主持证，再用主持证（主持模式）
```

**一轮对话里不许切身份。** 要切就发新请求、换凭证。服务端凭「请求带的是哪把钥匙」判定，
客户端声称什么都没用。

### 11.3 开房流程（v1.1 新增，回答「主持人 AI 怎么自己发起体验」）

**答案：不能。必须玩家发起。**

理由：开房要占额度。额度要么是玩家自己的免费次数，要么是站长办活动的预算。
**主持人 AI 没有钱包**——这也正是用户说的「钱由用户自己出」。

```
① 玩家（网页上点「开始体验」，或在插件里带自己的钥匙）
       │  POST /api/host/session/start
       ▼

> `POST /api/host/session/start` 的两条实现约束（P2 第 1 步补）：
> 1. **同一主体在同一本剧本上重复开房，旧会话先被收掉**（`reason=aborted`）。
>    一张证就是一把汤底的钥匙，不复用等于「点一下换一把」。
> 2. **限额**：登录 200 次 / 游客 20 次（`guest_counter` 落库，2 worker 一致）。
>    超限 429 `rate_limited`。

② 服务端：校验玩家身份 → 查额度（免费活动 / 玩家自填 Key）→ 扣额度
       │  建会话，phase = hosting
       ▼
③ 服务端返回 { session_id, host_token, expires_at }
       │
       ▼
④ 把 host_token 交给主持人 AI（插件自己收下，或玩家复制粘贴给别的 AI）
       │
       ▼
⑤ 主持人 AI 凭主持证主持这一场
```

**推论：**

- **插件带玩家钥匙** → 插件可以自己开房（相当于玩家本人在操作），**走玩家额度**
- **插件只有主持证** → 只能主持已开的房，**不能开新房**
- **纯第三方主持人（没有玩家钥匙）** → 只能等玩家先开房给它主持证
- 想让 AI 自己开房，等于给它一个「免额度开房」的后门——**v1.1 明确不做**

> 这就是用户原话「玩家用插件只能让 AI 调插件，那个 AI 成为主持人」的真实含义：
> **是玩家先给 AI 开了房，它才成为主持人的。**

## 13. 验收标准（进 CI）

### 13.1 静态断言

1. **上下文一致性**：20 组 `(state, npc_id, session)` 黄金样本，后端组装结果与现网前端

2. **标记解析一致性**：100 条真实 AI 输出，认字结果（正文 / 分段 / 标记）完全相同。

4. **权限矩阵逐格断言**：`guest` 与 `host` 绝不能拿到对方的能力。

### 13.2 运行时断言（v1.1 新增）

5. **指纹校验**：双跑期前端回算 `prompt_hash`，不一致必须告警（§4.2）。
6. **负样本泄露检测**（对应评审第 7 条「单点失效」）：
   构造一批「不该看到主持专用内容」的主体（游客、无订阅普通用户、只有 `script:read_answer` 的用户），

## 14. 防泄露三道防线（v1.1 新增）

**先说结论：只要客户端拿到了明文，它想存就存、想转就转，任何技术手段都拦不住。**
能做的是「缩短暴露窗口 + 泄露后可溯源 + 全程留痕」，**不能做的是「禁止」**。

| 防线 | 做法 |
|---|---|
| **一、缩短窗口** | 主持证短期有效（4h 封顶）、每次请求续期、结算/中止/闲置立即撤销（§7.4）。汤底只在主持期间可见，主持一结束就再也取不到 |
| **二、可溯源** | 返回的主持专用文本里嵌入**不可见标记**（零宽字符编码），内容包含「哪个玩家 / 哪张主持证 / 什么时间」。一旦汤底外泄，能查出是谁取走的 |
| **三、全程留痕** | 每次取主持上下文都记审计日志：主体、剧本、会话、时间、`prompt_hash`。异常模式（同一账号短时间取大量不同剧本的主持上下文）触发告警 |

> **明确声明**：本契约**不承诺**阻止客户端保存或转发 `system_prompt`。
> 安全边界止于「控制谁能取到」+「取走之后能查出来」。

## 15. 凭证权限语义（v1.1 新增，回答「老钥匙怎么拿到新能力」）

### 15.1 长期钥匙的 `scopes` 是「上限」，不是「快照」

```
实际生效能力 = 钥匙上的 scopes  ∩  该用户当前本该拥有的能力
```

取交集而不是直接采用，好处是双向收紧：

- 用户被降权 → 钥匙自动跟着受限
- 钥匙只授权了一部分 → 只能干那一部分

### 15.2 新增能力不自动给老钥匙

安全上必须默认最小权限。想要新能力，用户重新生成一次钥匙。

### 15.3 钥匙里出现系统不认识的 `scope`

**忽略并记一条告警，不要拒绝。**

理由：一旦拒绝，所有老钥匙会在版本升级的瞬间全部失效——那是灾难。
但若解析完之后 `scopes` 为空集，则**拒绝**（这把钥匙等于什么都不能干）。

## 16. 降级策略（v1.1 统一表述，回答评审第 6 条）

v1 一边写「不一致直接报错不用降级」，一边写「接口失败时回退本地实现」，读起来自相矛盾。
**其实说的是两件不同的事：**

| 情况 | 服务端状态 | 消费端行为 |
|---|---|---|
| **不一致** | 服务端活着、正常返回，但结果与本地实现算的不一样 | **不许静默用本地的**。用服务端的，同时上报告警——说明有一份实现写错了 |
| **不可用** | 连不上 / 5xx / 超时 / 契约版本对不上 | 降级用本地实现，**必须打标记 + 上报**，不许悄无声息 |

判定顺序：先看**可达性**，再看**一致性**。

## 17. 提示词文件写入安全（v1.1 新增，回答评审第 15 条）

现状（已核实）：管理面板保存提示词是**直接覆盖写文件**，没有临时文件、没有备份、没有原子替换。
保存一次，前一版永久消失，服务器上没有任何撤销手段。

**强制要求（所有写 `npc_configs/**` 的地方）：**

1. 先写同目录下的临时文件
2. `flush` + `fsync` 落盘
3. 用**原子替换**覆盖目标文件（同一文件系统内的 rename 是原子的）
4. 覆盖前把旧文件另存为 `{name}.bak`（**只保留上一版**，不做无限版本堆叠）
5. 任何一步失败 → 目标文件保持原样，返回错误，不许留下半截文件

> 这条不只管提示词，`config.json`、表情动画配置等所有 `npc_configs/**` 下的写入都要遵守。
